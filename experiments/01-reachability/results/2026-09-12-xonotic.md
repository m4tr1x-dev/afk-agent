# Xonotic 0.8.6, 2026-09-12 — no verdict

**Question 1 is not answered by this run, and that is the correct outcome.**

## What happened

| Run | Result |
| --- | --- |
| 1 | Complete report. Every measurement: lag 0, confidence **1.000**. Verdict "NOT REACHED by relative movement" |
| 2 | Refused to run. Liveness check: 13 consecutive captures pixel-identical |
| 3 | Refused to run. Per route: `PrintWindow` static across 12 frames, `BitBlt` static across 12 frames |

Run 1 is the interesting one. It produced a confident, complete, well-formatted
answer to the question that gates the project, and that answer was **wrong** —
not because the camera failed to turn, but because every pair of frames was
identical, and two identical frames correlate perfectly at zero displacement.

A correlation of exactly 1.000 is not a measurement. It is the signature of
comparing something with itself.

The liveness precondition was added because of run 1, and runs 2 and 3 are it
working. A probe that refuses to answer is worth more than one that answers
wrongly, because the wrong answer here reads as "this project does not exist".

## What the game was actually doing

Established by capturing the window's screen rectangle directly, outside the
probe:

- The map loaded. Gametype Capture the Flag, map Dance.
- A first-run dialog asked whether to allow player statistics to use the
  nickname. Answered by setting `cl_allow_uidtracking 0` and
  `cl_allow_uid2name 0` on the command line — the privacy-preserving values,
  and the ones the dialog asks about — rather than by clicking a consent
  prompt.
- The game then sat on a **Join / Spectate** prompt with the world **paused**.
  `+defer 12 "cmd join"` did not dismiss it.

Five captures of the window rectangle taken half a second apart were
**identical**. The scene was genuinely not animating.

## What this does and does not establish

**Establishes:** the probe runs end to end against a real game window; the
window is found by title; the foreground guard admits it; both capture routes
return frames with content; the liveness precondition fires when it should.

**Does not establish anything about capture.** The tempting conclusion — that
the drawing interface returns a stale image for an OpenGL window, which would
be a finding for `ADR-0008` — is **not supported by this run**. The window was
not animating on screen either, so a static capture is exactly what a correct
capture would produce. The two explanations are not separated yet, and writing
down the more interesting one would be a guess.

Separating them needs one run against a window that is demonstrably animating.

## What blocks the answer

The game must be in live gameplay, and reaching that state needs a click on
`Join`.

- The probe cannot click: `afk-input` carries pointer movement only, by design
  for this milestone.
- Computer use cannot reach it either: Xonotic installs through a package
  manager rather than the Start menu, and `request_access` does not resolve it
  by name.

Two ways forward, in order of preference:

1. **Breathedge**, which is in the application list and is reachable by computer
   use. Unreal Engine 4, first person, mouse look — a commercial engine, which
   is closer to what the project is actually aimed at than a community shooter.
2. **Button support in `afk-input`**, which the action vocabulary requires
   anyway (`click`, `press_pointer`, `release_pointer`). It is the larger piece
   of work and it belongs to M3 rather than to a probe, but it removes the
   dependency on anything outside the project.

## The run-1 lesson, stated plainly

The probe was written with three null controls precisely so that a positive
result could not be a coincidence. It had no control for the case where the
measurement apparatus reports perfect agreement, and that is the case that
produced a confident false negative on the project's gating question.

A control that catches a false positive does not catch a false negative. Both
need designing for.
